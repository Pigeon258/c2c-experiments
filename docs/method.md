# 实验设计

## 训练与选权

两个基础模型使用各自固定版本的 Qwen3，冻结参数，只训练接收端的缓存融合器。从末层反向一一对应，共 28 对。M2 的接收端有 36 层，浅层 0–7 保留自己的缓存。融合器共 529,228,280 个可训练参数。三个方向分别从头训练。

OpenHermes-2.5 取固定版本的前 500,000 条，按完整对话模板长度 ≤ 2,048 筛出 498,807 条。使用独立随机种子 42 做 99/1 划分，移除训练集中 3 条与 GSM8K 测试题重合的记录，最终训练 493,815 条、验证 4,989 条。训练时关闭 thinking，用参考回答计算接收端的下一个 token 损失。

每次更新累积 256 个样本，按有效监督 token 数加权。一个 epoch 共 1,929 次更新，最后一次为 247 条。AdamW 初始设置见 [M1 配置](../experiments/configs/M1.json)，峰值学习率为 0.0001，线性调度，预热 192 步。门温度从 1 线性降至 0.001。M2 启用反传激活的 CPU 卸载。

每 100 次更新及 epoch 结束时做完整验证，共 20 次。最低验证损失对应的更新步为 M1 1,900、M2 1,929、M3 1,900。[三个方向的最低与最终损失](../experiments/records/training.json)

## 输入与通信

| 协议 | 发送端起初可见 | 接收端起初可见 | 融合前怎样补齐 |
|---|---|---|---|
| P1 | 完整输入 | 完整输入 | 直接使用双方缓存 |
| P2 | 题目及 5 段证据 | 题目及另外 5 段证据 | 双向交换缺少的段落，双方重新 Prefill |
| P3 | 题目及全部证据 | 题目 | 发送端补传全部证据，接收端重新 Prefill |
| P4 | 完整输入 | 固定占位提示 | 发送端补传题目及可用证据，接收端重新 Prefill |

数学与代码测试 P1、P4。问答测试四个协议。P2 要求 10 段不同标题的证据、恰好 2 段支持证据，双方各分 1 段支持和 4 段干扰，因此适用 7,345 题。其他问答协议各有 7,405 题，跨协议比较用共同的 7,345 题。

双方最终使用同一序列。发送端将完整源 KV 搬到 CPU、序列化并通过同机 TCP 回环传输。接收端恢复缓存，在 GPU 上转换并融合，再逐 token 生成回答。记录的通信量是应用层字节，含帧头。模型在同一张 RTX 3090 上执行，墙钟时间反映此部署。环境和线程配置见[运行环境](../experiments/environment.json)。

## 计分

GSM8K 解析输出中首个符合 `#### 数字` 的答案。HotpotQA 计算完整回答归一化后的 EM 和词级 F1。HumanEval 将原始函数前缀与生成文本直接拼接，用原题测试运行一次。三个数据集分别使用 main/test、distractor/validation 和全部 164 题。贪心解码最多生成 1,024 个新 token，遇 EOS 提前停止。

正式报告使用固定分母，另按相同题号和顺序给出问答共同子集。各协议报告附均值、95% bootstrap 区间及分项成本。逐题 T2T 配对差值在这批报告中尚无结果。
